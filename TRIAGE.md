# NETVERSE Community Triage Guide

This guide explains how public community reports should be handled without exposing private production information.

## Intake

Public issues should be limited to reproducible public-facing problems, documentation improvements, accessibility feedback, community requests and product ideas that are safe to discuss publicly.

Security vulnerabilities, credentials, private keys, tokens, seed phrases, sensitive infrastructure details and proprietary production code must not be posted publicly.

## Suggested triage

### Bug

Confirm that the report contains reproducible steps, expected behavior and enough non-sensitive context to understand the problem.

### Feature or UI idea

Identify the user problem first. Separate the requested solution from the underlying need and avoid treating submission as a commitment to implement.

### Documentation or community request

Confirm the affected public page/channel and the requested change. Prefer small, verifiable public improvements.

### Launch readiness

Use launch-readiness reports only for public process or documentation gaps. Do not request or expose private infrastructure evidence in public issues.

## Priority principles

1. Security and privacy risks are routed privately.
2. Problems blocking safe public participation come before cosmetic improvements.
3. Reproducible issues are easier to act on than general reports.
4. Public discussion must stay within the scope of this repository.
5. Roadmap items are planning direction, not delivery promises.

## Closing issues

When possible, close an issue with a short explanation and link to the public change, documentation or decision that resolved it.
